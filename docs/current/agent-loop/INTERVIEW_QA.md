# Agent Loop 与受控自进化面试问答

> 用途：准备 Agent Loop、上下文工程、工作流可靠性和受控自进化相关面试。
>
> 使用方式：先理解每个答案背后的状态、边界和证据，再用自己的话复述。文中的
> TaskPacket、ContextBrief、RunManifest、TestReport 等是项目中的固定工件名称；
> 其他英文只在它是代码、协议或行业固定名词时保留。
>
> 真实性边界：本项目的本地 Codex CLI 宿主、串行多角色流程、独立测试、有限恢复、
> Docker 测试、隔离集成和受控经验治理已经实现并有现场证据。Desktop/MCP 宿主适配、
> 自动修复、自动部署、自动训练和正式模型变更不属于当前默认能力。当前状态以
> [CURRENT_STATE.md](CURRENT_STATE.md) 为准。

## 第一部分：Agent Loop 30 问

### 1. 什么是 Agent Loop？

答：Agent Loop 是把一次长任务表示为有边界的状态机。每一轮读取当前任务状态和最新观察，由模型选择下一步动作，工具执行动作后更新结构化状态，再进入验证、恢复或结束分支。它不是让模型无限聊天，而是让模型成为状态机中的一个决策节点。

### 2. Agent Loop 和普通聊天有什么区别？

答：普通聊天主要依赖对话历史维持上下文，任务状态常常隐含在文本中。Agent Loop 把任务范围、责任人、预算、快照、验证要求和停止条件显式保存，因此可以检查、恢复、审计和复现。即使更换会话，也可以从结构化工件恢复，而不是依赖旧聊天记忆。

### 3. 为什么不能只使用 ReAct 式的“思考—行动—观察”？

答：ReAct 可以描述单轮工具使用，但如果不断追加全部思考、工具输出和历史观察，长任务会出现上下文膨胀、旧事实污染和成本上升。这个项目在 ReAct 的动作循环之外增加了 TaskPacket、ContextBrief、状态持久化、验证闸门和恢复策略，使执行过程有明确的生命周期。论文 SKILL.state 进一步强调，后续步骤应优先使用当前结构化状态，而不是重新读取整段历史。

### 4. Agent Loop 的最小状态是什么？

答：至少包括任务身份、当前阶段、Owner、基线或最终提交快照、允许修改范围、预算计数器、最近动作、失败分类、恢复次数和下一步允许的状态转换。模型的中间推理不是长期状态；它可以被审计系统脱敏保存，但不应原样进入下一轮上下文。

### 5. TaskPacket 解决什么问题？

答：TaskPacket 是一次任务的不可变边界，描述任务身份、责任域、基线快照、允许写入路径、测试范围、Docker 要求、预算、恢复上限和验收条件。它回答“这次任务允许做什么”，而不是“模型应该怎么思考”。后续 Owner、Test 和集成都必须服从同一个 TaskPacket。

### 6. ContextBrief 和 TaskPacket 有什么区别？

答：TaskPacket 定义硬边界，ContextBrief 组织完成任务所需的最小事实。ContextBrief 通常包含事实来源图、已知事实、假设、未知项、相关经验以及实际装入和排除的上下文。前者决定权限和范围，后者帮助 Agent 在范围内正确工作；经验不能反过来覆盖 TaskPacket。

### 7. 如何避免上下文污染？

答：先读取权威规则、当前状态和任务边界，再读取对应领域任务卡、Skill、contract 和最近回归；子任务只接收声明的结构化工件，不接收父对话全文、全仓库扫描结果和无关历史归档。历史日志用于审计，当前状态用于决策，两者不能混用。

### 8. 什么是上下文的权威顺序？

答：权威顺序是发生冲突时的裁决规则。例如，当前 contract 和 Skill 约束优先于候选 Lesson，当前 TaskPacket 优先于经验建议，当前 Git snapshot 优先于聊天中提到的旧提交。无法判断哪一份事实权威时不猜测，直接停止为 HUMAN_REQUIRED。

### 9. 为什么默认采用串行而不是并行？

答：这个工作流存在明确依赖：一个 Owner 先产生最终提交，独立 Test 再从该提交验证，之后才可能集成。并行写入会增加工作树冲突、状态同步、责任归属和证据绑定的复杂度。当前目标是可靠完成一条责任链，而不是让多个 Agent 同时修改同一任务。

### 10. 四个专业 Agent 分别负责什么？

答：Core 负责规则、合法动作、Schema 和 ABI；Trainer 负责 PPO、Collector、Reward、训练任务和模型来源；Product 负责 React、FastAPI、HTTP 契约和用户界面；Teacher 负责结构化证据、解释和隐私。划分依据是事实来源和修改边界，不是编程语言。

### 11. 为什么不增加一个独立的 Manager Agent？

答：主 Codex 确实承担编排职责：理解目标、选择责任域、生成任务上下文、调用 Owner 和 Test、检查报告并推进生命周期。从广义上说，它是编排器，具有部分管理功能；但它不是第五个业务 Owner，也不应该替 Core、Trainer、Product 或 Teacher 定义领域事实。这里“不增加 Manager Agent”指不再额外引入一个拥有独立业务权限、会重复路由并可能越权修改的模型角色。

### 12. Owner 和 Test Agent 为什么必须分离？

答：Owner 负责实现，Test Agent 负责独立判断结果是否满足功能、contract、文件范围和证据要求。如果 Test 读取 Owner 的实现过程，就可能被原有假设影响，独立性会下降。Test Agent 从 Owner 的最终提交开始，因此“实现者认为正确”不能直接变成 PASS。

### 13. Test Agent 能修改代码吗？

答：它可以在 TaskPacket 声明的测试写入目录内修改测试，但不能修改生产代码、降低断言或改变 contract 来制造 PASS。测试标准和测试修改还要由领域 Owner 或人工闸门复核。发现生产缺陷时，Test Agent 应输出失败分类并交回对应 Owner。

### 14. 什么是 Host Bridge？

答：Host Bridge 是 Agent Loop 和具体宿主平台之间的适配层。它把验证过的任务规格转换为宿主任务，保存宿主会话、进程、工作树和任务身份，并把创建、等待、恢复、关闭结果映射回统一的 Runner 事件。这样控制面不需要把某个宿主的接口细节散落到业务逻辑中。

### 15. create、wait、rebind、close 分别做什么？

答：create 创建一个新的子任务并保存其宿主引用；wait 等待并读取任务状态和结构化输出；rebind 在调度器或宿主进程重启后重新连接原任务；close 在报告、预算和范围检查通过后关闭任务并收集最终结果。恢复时使用 rebind，不应该把原任务误当成新任务再次 create。

### 16. 进程重启后如何恢复任务？

答：控制面先从持久化注册表读取 task identity、runner_ref、进程信息、工作树和最近状态，然后调用宿主的 lookup/rebind。重绑定成功后继续原责任链，并记录恢复事件；找不到原任务、身份不匹配或恢复点不明确时停止，不创建一个看似相同的新任务。

### 17. 为什么需要 Git snapshot 和隔离 worktree？

答：snapshot 提供可复现的代码基线，worktree 把 Owner 的修改与父工作树隔离。这样 Test 可以验证准确的最终提交，集成可以检查 changed paths，回滚也不会覆盖无关用户改动。脏 parent 中的直接合并属于人工边界，不是普通自动步骤。

### 18. 如何控制无限循环？

答：TaskPacket 规定最大尝试次数、恢复次数、模型回合、token、等待时间和总耗时；状态机还规定哪些失败允许恢复、哪些失败只能停止。预算耗尽后不再启动新的模型工作。单个 Agent 的预算不够时，仍要检查整个任务预算，而不能把任务拆开来规避上限。

### 19. 为什么要区分 resume、retry 和 return to owner？

答：resume 是同一次逻辑尝试在原 Runner 上恢复，通常用于宿主进程或 Runner 丢失；retry 是验证步骤在允许范围内重跑；return to owner 是把已确认的生产缺陷交回原领域 Owner 修复。三者的责任、模型消耗、证据和上限不同，不能都叫“再试一次”。

### 20. 失败应该如何分类？

答：至少区分代码缺陷、contract 缺陷、环境失败、Docker 失败、权限失败、协议失败、flaky、预算耗尽和宿主恢复失败。分类决定下一步是回到 Owner、等待人工、有限恢复还是立即停止。把环境问题伪装成代码问题，会导致错误修改；把代码问题伪装成环境问题，会掩盖缺陷。

### 21. 什么是 HUMAN_REQUIRED？

答：它不是普通失败，而是系统无法安全自动判断的边界状态。例如权限不足、父工作树有无法归属的改动、Docker 资源所有权不清、contract 语义冲突、隐私风险或宿主无法证明重绑定。进入该状态后要保存原因和证据，等待人工决定，不能靠重复调用绕过。

### 22. Docker 在 Loop 中什么时候启动？

答：只有 TaskPacket 和 TestMatrix 明确声明服务依赖或容器测试时才启动。Test Agent 必须使用 allowlist、隔离项目名、健康检查、日志证据和 cleanup；不能执行共享环境的全局 down。Docker 不可用时应报告 DOCKER_FAILURE 或 PERMISSION_REQUIRED，不能把主机上的半套依赖测试当成最终 PASS。

### 23. RunManifest 有什么作用？

答：RunManifest 是一次 Loop 的运行账本，记录角色运行、宿主事件、模型调用、token、耗时、恢复次数、状态转换、报告引用、失败分类和终止原因。它把“发生过什么”绑定到任务身份和 snapshot。没有完整账本，即使代码测试通过，也不能形成完整的现场证据。

### 24. TestReport 和 IntegrationManifest 有什么区别？

答：TestReport 说明独立验证实际执行了什么、结果如何、环境和 Docker 证据是什么；IntegrationManifest 说明候选如何在隔离环境中应用、最终提交是什么、范围和 contract 是否满足、如何回滚。前者证明“结果可验证”，后者证明“集成可控”。

### 25. 如何避免重复创建子任务？

答：为每个任务保存稳定的 task identity 和 runner_ref，并把宿主会话注册持久化。恢复时先 lookup/rebind，只有明确不存在且任务状态允许新建时才 create。外部动作还应尽量带幂等键或状态检查，不能用“创建失败了所以再创建一次”替代状态查询。

### 26. 这个系统能保证 exactly-once 吗？

答：不能笼统声称所有外部动作都是 exactly-once。当前实现重点是持久化状态、避免重复 create、让恢复绑定原 Runner，并对不确定状态 fail-closed。外部 API 仍可能是至少一次语义，因此需要幂等操作、重复检测和人工闸门来降低副作用。

### 27. 如何处理隐私和提示注入风险？

答：子任务只获得声明范围内的文件、contract 和结构化上下文，经验和日志必须脱敏，禁止把完整 prompt、cookie、token、隐藏手牌或未公开候选动作写入长期工件。Teacher 只能解释已执行的结构化证据，不能借助上下文推断并泄露隐藏信息。发现隐私边界不确定时停止，而不是让模型自行判断可以公开。

### 28. 如何评价 Agent Loop 是否有效？

答：不能只看最终成功率，还要看重复失败次数、无效工具调用、上下文 token、总耗时、恢复成功率、独立验证通过率、错误分类准确性、越权修改次数和人工介入次数。对长任务还要比较 prompt 是否随执行轮数无界增长。评价必须包含失败和反例，而不是只展示成功案例。

### 29. 当前 Agent Loop 的主要限制是什么？

答：当前已验证的是本地 Codex CLI 宿主的受限串行路径，Desktop/MCP 宿主仍是可选适配；自动修复、并行调度、部署、模型训练和模型 promotion 默认关闭。Docker 也不是所有任务的默认依赖，必须由任务明确声明。回答这些限制比声称“完全自治”更准确。

### 30. 如何用一分钟介绍这个 Agent Loop 项目？

答：我构建了一个受限串行的 Coding Agent Loop，把一次长任务表示成带预算、快照、权限和验收条件的结构化状态。系统先路由到一个专业 Owner，再由独立 Test Agent 从最终提交进行验证，并通过宿主重绑定、运行清单、Docker 证据和隔离集成支持恢复与审计。失败不会无限重试，而是分类、有限恢复，并把成功的执行经验交给后续自进化流程。

## 第二部分：受控自进化 30 问

### 1. 这个项目中的“自进化”是什么意思？

答：自进化指系统从已完成任务的执行记录、失败、回退和验证结果中提取可复用经验，以便后续在相同条件下减少已证明的弯路。它首先改进的是上下文装配和流程决策，不是直接修改模型参数或生产代码。

### 2. 自进化不是什么？

答：它不是模型自由修改自身，不是失败后无限重试，也不是把一次偶然成功永久写成规则。它也不等于在线训练、自动修改 Skill、自动修改调度器或自动部署。经验必须经过证据、回归和人工边界控制。

### 3. 为什么把“弯路分析”放在自进化的第一优先级？

答：长任务中最容易重复发生的成本不是单次推理，而是错误入口、错误环境、无效命令和没有必要的重复尝试。先识别这些可避免弯路，可以在不改变模型的情况下减少时间和 token 消耗。只有先证明某条路径确实可避免，后续经验才有可靠含义。

### 4. 什么是 PathAnalysis？

答：PathAnalysis 比较计划步骤和实际步骤，统计失败动作、重复动作、可避免弯路、必要探索、成功回退、额外工具调用、额外模型回合和额外耗时。它描述执行路径，不替代测试报告，也不自行推断没有证据支持的根因。

### 5. 什么是 DetourRecord？

答：DetourRecord 是一条可审计的弯路记录，包含触发条件、失败工具和操作、错误分类、规范化失败签名、可见前置事实、影响、成功替代路径、避免规则和证据引用。它必须绑定任务、snapshot、RunManifest、Trace 或 TestReport，不能只保存一句自然语言总结。

### 6. 必要探索和可避免弯路有什么区别？

答：第一次检查未知环境、发现新 contract 问题或请求明确权限，事前无法合理避免时属于必要探索。若在已知 Docker 不可用后重复启动、已有成功替代方案却再次使用失败命令，或者已有前置检查却没有执行，就可能是可避免弯路。判断依据是当时可见的结构化事实，而不是事后责怪 Agent。

### 7. 为什么不能写“某工具失败，以后永远不用它”？

答：工具失败通常依赖触发条件，例如脏工作树、权限、路径、参数或环境。正确经验应写成“在这些条件下避免某种操作，优先使用经过验证的替代方案”，而不是永久禁用工具。没有条件的绝对规则很容易误伤未来完全不同的任务。

### 8. 什么是失败签名？

答：失败签名是对失败动作、失败分类和关键前置条件的脱敏、规范化表示，用于判断两个失败是否属于同一类。它不保存 token、cookie、完整命令或完整 prompt。只有签名、条件和证据都匹配时，系统才可以判断是否重复失败。

### 9. 什么是 Candidate Lesson？

答：Candidate Lesson 是从结构化执行证据中提取的候选经验，通常描述触发条件、应避免的动作、优先路径、前置检查和证据引用。它默认只写入 candidate-only 工件，不会自动改变下一次任务的上下文、Skill 或调度规则。

### 10. 什么是 Retry Learning Gate？

答：Retry Learning Gate 是模型消耗型重试之前的检查器。它要求重试携带脱敏失败签名、改变的引用、下一次前置检查、成功替代动作以及前置条件是否变化。缺少这些信息，或者信息与之前完全相同，就不允许继续消耗模型。

### 11. 什么是 learning delta？

答：learning delta 是本次重试相对于失败尝试的结构化变化，例如改用了不同的文件范围、先执行了新的环境检查、换用了已验证的操作或修正了错误 contract 入口。它不是一句“再试一次”，而是可以被检查器比较的改变项。没有真实变化就不能把重复调用包装成学习。

### 12. 为什么同一失败且没有新变化时必须停止？

答：因为相同失败签名、相同前置条件和相同 learning delta 意味着系统没有获得新的信息。继续调用只会增加 token、耗时和副作用，不会提高成功概率。停止状态应记录为 STOP_NO_LEARNING，并保留人工介入入口。

### 13. resume 也必须生成 Lesson 吗？

答：不一定。丢失 Runner 后在同一责任链上成功 resume，是恢复同一次逻辑尝试，不代表发现了新的可复用经验。只有发生了有证据的替代路径或重试变化，才需要通过 Retry Learning Gate 形成候选 Lesson。

### 14. 为什么成功重试后还只是 candidate？

答：一次成功可能来自偶然的环境状态、特殊 snapshot、临时权限或错误的根因判断。candidate 状态把“这次执行观察到的事实”和“可以推广的规则”分开，避免一次成功污染所有后续任务。后续必须通过独立证据和固定回归，才能提高可信度。

### 15. E2 Shadow Retrieval 做什么？

答：Shadow Retrieval 在不改变当前任务上下文的情况下，模拟检索哪些经验会命中、哪些会被排除，并记录原因、匹配字段、估算 token 和模型调用数。它的价值是先观察经验检索效果，避免一开始就把未经验证的 Lesson 注入 Agent。

### 16. E3 Advisory Context 是什么？

答：E3 把已经允许使用的经验放入 ContextBrief 的 advisory 区域，作为非权威建议。它必须保留触发条件、避免动作、优先动作、前置检查、来源和 snapshot，且有数量和 token 上限。advisory 不能写入事实底座、权限、预算、并发和停止条件。

### 17. advisory 和权威事实有什么区别？

答：权威事实来自当前 contract、Skill、TaskPacket、代码和验证过的状态，决定系统必须遵守什么。advisory 只是经验建议，告诉 Agent 在类似条件下可以优先考虑什么。两者冲突时权威事实获胜；经验不能以“历史上成功过”为理由绕过当前边界。

### 18. 如何防止错误 Lesson 进入上下文？

答：检索前检查状态、责任域、任务类型、文件范围、contract 版本、snapshot 兼容性、验证日期和冲突标记；候选、拒绝、过期、不兼容和缺少证据的 Lesson 必须排除。注入时还要限制条数和 token，并记录采用或未采用的结果。

### 19. E4 固定回归要验证什么？

答：E4 比较 Baseline 和 Evolved 两种上下文或经验策略下的结果，检查任务成功率、可避免弯路、额外工具调用、模型回合、上下文 token、恢复耗时、contract、范围、隐私、错误规避和负向迁移。它不仅要证明目标任务改善，还要证明安全和控制任务没有变差。

### 20. 为什么回归集要包含 target、control 和 safety？

答：target 用于确认经验确实改善目标问题；control 用于确认经验不会改变不相关任务；safety 用于确认经验不会导致越权、隐私泄露、错误放宽或违反停止条件。只有 target 变好而 control 或 safety 变坏，不能算成功。

### 21. 什么是 false avoidance 和 negative transfer？

答：false avoidance 是系统把本来有效、必要的动作误判成弯路，导致后续任务不敢执行。negative transfer 是经验在原任务上有帮助，却损害了其他任务、其他环境或安全边界。两者都必须在 E4 中显式统计，不能只看目标任务的成功率。

### 22. 为什么需要两个独立 Lesson 才能形成更高层提案？

答：一个 Lesson 可能只是某个任务、snapshot、权限或临时环境的偶然现象。两个独立 Lesson 需要有不同 detour、不同证据来源和可区分的 snapshot，同时触发条件和成功路径具有一致性，这才说明经验可能具有跨任务稳定性。它是最低限度的重复验证，不是为了形式主义增加文档。

### 23. E5 Proposal 和正式修改有什么区别？

答：E5 只生成只读提案，例如 Skill、路由或验证规则的草案，并携带来源 Lesson、触发条件、反例和回归证据。它不会直接修改 AGENTS.md、Skill、Scheduler、contract、权限、预算或生产代码。正式修改必须经过额外人工批准和独立验证。

### 24. 为什么自进化不能自动修改 Skill？

答：Skill 会影响未来大量任务，错误修改的影响范围远大于单次任务。候选经验往往只证明了局部条件下的成功路径，还没有证明适用范围、反例和安全边界。把提案和正式规则分开，可以让系统学习，同时避免未经审核的规则扩散。

### 25. E6 Training Readiness 做什么？

答：E6 只审查经验是否具备交给 Trainer 评估的前置条件，例如 E4 批准、正式规则批准、独立稳定性证据、当前 observation/action/reward contract 固定、训练任务已校验以及评估结果完整。它不启动训练、不加载模型、不修改模型或训练配置。

### 26. 自进化和模型训练有什么区别？

答：自进化当前主要是符号化的经验治理：记录路径、提取 Lesson、检索建议和回归规则。模型训练则是修改参数，需要独立的数据、算法、训练任务、预算、评估和 promotion 流程。前者可以先减少流程弯路，不能被描述成模型已经自动学会新能力。

### 27. 如何衡量一条经验带来了多少收益？

答：需要把采用经验的结果与可比较的 Baseline 对照，记录节省的工具调用、模型回合、token 和耗时，同时确认成功率和安全指标没有下降。没有反事实 Baseline 时，节省值应标记为 unavailable，不能把没有测量说成节省为零。

### 28. 请举一个本项目中的自进化例子。

答：如果在跨工作树集成时，Agent 使用带索引的补丁操作失败，随后在明确文件范围内使用路径限定的补丁并通过逐路径提交成功，那么系统应记录脏 parent、跨工作树和索引不一致这些触发条件。后续相同条件下优先做状态检查和路径限定操作，但该经验仍需经过候选、检索、回归和人工闸门，不能直接变成永久规则。

### 29. 什么是错误的自进化例子？

答：例如只因为一次 Docker 启动失败，就记录“永远不要使用 Docker”；或者只因为一次权限错误，就让所有后续任务跳过测试。这些记录没有条件化，也没有区分环境失败和代码失败，容易产生错误规避和负向迁移。正确做法是记录具体环境、失败签名、权限状态和经过验证的替代方案。

### 30. 这个自进化架构下一步最值得改进什么？

答：优先把每次模型调用的当前执行状态、最新观察、状态增量和验证结果进一步标准化，并测量上下文长度、累计 token 和恢复成功率。其次增加来自不同任务和不同环境的独立 Lesson，完善反例回归，再考虑是否形成只读 Proposal。任何正式规则变化或训练仍应保持独立人工闸门。

## 面试时必须记住的总答案

### Agent Loop

Agent Loop 是有界状态机，不是无限聊天。它用 TaskPacket 定义硬边界，用 ContextBrief 装配最小事实，用专业 Agent 实施，用独立 Test 验证，用 snapshot 和 RunManifest 保证可复现与审计，用恢复策略处理有限失败。

### 自进化

自进化不是自动改代码或自动训练，而是从执行日志中识别可避免弯路，经过 Retry Learning Gate 产生候选经验，再通过检索、固定回归和人工批准形成只读改进提案。相同失败且没有新的学习增量时必须停止。

### 最容易被追问的边界

当前真实完成的是本地 Codex CLI 宿主的受限串行流程和经验治理控制面；Desktop/MCP 宿主、自动修复、并行调度、正式训练和模型变更仍然关闭。能够清楚说出这些限制，本身就是可靠性设计的一部分。
